# Movement Map — Principles

These principles guide product and technical decisions. When a new feature conflicts with them, the conflict should be resolved intentionally rather than allowing the application to drift into a conventional fitness-app model.

## 1. Meet the Person Where They Are

The user should not have to become more capable before the application becomes useful.

Different starting points, energy levels, capabilities, equipment situations, and movement preferences should have legitimate paths through the application.

## 2. Help Them Understand Where They Can Go Next

Movement Map should not stop at "do this exercise."

Whenever practical, it should explain relationships between movements, capacities, skills, and progressions.

## 3. Reduce Decision Fatigue

The application should reduce unnecessary choices rather than creating an enormous catalog and calling that flexibility.

Filters, curation, recent activity, categories, and targets should do useful decision-making work for the user.

## 4. Accessibility Is Fundamental

Accessibility is part of the product's foundation, not a later accessibility pass.

The system should be capable of representing different starting positions, support requirements, ranges, and capability constraints as the movement library develops.

## 5. Movement Is Connected

Movement should be represented as a connected system rather than isolated exercises.

Joints, muscles, movement chains, movement categories, patterns, and skills can all provide useful context.

## 6. Build From the Ground Up

Movement Map values foundational movement and mobility while recognizing that foundational work can contribute to more advanced skills.

The product should make those relationships visible without implying that every user must pursue advanced skills.

## 7. Curation Without Rigidity

Recommendations should guide without trapping the user.

The system can recognize what has already been done and what may be underrepresented without treating a weekly balance as a set of mandatory rules.

## 8. One Exercise, Many Uses

An exercise should be defined once and made accessible to multiple routines, cards, sequences, and future experiences where appropriate.

## 9. The Practical Unit of Action Is Mode-Appropriate

The practical unit of action depends on the Mode.

In Flow Day and Grab & Go, that unit is the card. The user should be able to reference a card, perform what is on the card, and check off the card. Individual exercises are elements within cards, and separating every exercise into a separate completion action should be avoided when it introduces unnecessary friction.

In Full Body, that unit is the set. Full Body's execution model is intentionally different from the other Modes: sets are logged as they are performed, and the workout is marked finished at the end.

## 10. Morning Anchor Is an Anchor, Not a Requirement

The Morning Anchor is a foundational starting point within Flow Day, but it is not a requirement to use Movement Map.

A user who cannot or does not want to complete the full anchor should be able to pare it down or use Grab & Go instead.

## 11. Preserve User Agency

Customization should be possible without requiring users to rebuild the entire application.

The Morning Anchor is a key example: users should eventually be able to replace an exercise, add or remove a card, build their own anchor, and save it.

## 12. Education Should Be Useful at a Glance

Movement information should be concise enough to use during a session while still providing meaningful context.

Useful exercise information may include:

- Purpose
- Instructions
- Best practices
- Common mistakes
- Builds toward
- Supports
- Pairs well with
- Progression level
- Unlocks

## 13. Do Not Manufacture Pressure

Streaks, calorie targets, and similar mechanisms can be useful in some products but should not become the central motivational system of Movement Map.

The product should encourage movement without turning movement into another source of guilt or performance pressure.

## 14. Build the Product We Actually Need

Movement Map is its own first beta environment.

Features should solve real problems encountered during actual use rather than being added because conventional fitness applications have them.

## 15. One Thing at a Time

The vision can be ambitious while the implementation remains incremental.

Future possibilities belong in the roadmap until the current foundation is strong enough to support them.
